# 整改经验与后续质量门槛

2026-10-20。

1. **内部格式不能代替入口。**原 JSONL 有利于核心实现，却把适配成本转移给用户。现在同时保留内部格式和实际 trace/宿主入口；新增场景必须先证明输入可取得。
2. **边界相似不代表语义相同。**didChange 顺序编辑、同基线 TextEdit、VS Code 事件要分开处理。追加实测发现重新排序 VS Code 事件会把同位置插入从 XY 变成 YX；现在保留宿主数组原顺序，与微软客户端转换器一致。独立宿主检查点捕获了原错误，不能用核心自己的结果生成“独立期望”。依据：https://github.com/microsoft/vscode-languageserver-node/blob/main/client/src/common/codeConverter.ts 。
3. **成功启动不等于测试完成。**本机 VS Code 启动器可能先返回 0；测试执行器因此增加完成结果等待和明确超时，缺失结果不能记为通过。
4. **UI 错误不应无限等待用户关闭通知。**实际用户命令测试暴露了错误提示阻塞；改为展示提示并传播失败，自动化调用可及时结束。
5. **“没有格式化编辑”存在两种原因。**文档已格式化和没有提供者不能混为一谈。错误信息明确两种可能，真实命令测试使用未格式化文档。
6. **测试环境也需要边界。**宿主配置包含套接字等文件，放在源码扫描树下会干扰编译；现移至忽略的 .tooling，并为每次运行建立新配置，避免旧的未保存文本污染结果。
7. **断言错误不能默默变成通过。**未知 expectation 字段、缺 actual、错 URI 和非法用例要失败/不完整；suite 继续运行后续用例并汇总最高退出状态。
8. **复现的意义要明确。**成功重现故障的用例可以通过，但嵌套分析仍失败；修复后的正确性用例应有独立文本/规则期望。两者不混淆。
9. **兼容性声明要小于或等于证据。**本轮只验证固定 trace 方言、VS Code 1.138.0 和本地 Windows 发行，不写“任意日志/所有编辑器/跨平台已全面验证”。
10. **技术证据不能解决全部需求质疑。**完整工程工作流能够回应接入与复用；需求规模和重复使用仍要真人试用。下一轮以真实维护者任务及负面反馈决定优先级。

新增功能进入主交付前必须同时有：可获得的真实输入、明确支持范围、可行动输出、独立或手工期望、失败路径、复用入口和事实一致的说明。测试数量、提交数量、功能列表均不能单独替代这些条件。
