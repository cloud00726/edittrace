# EditTrace 审查反馈整改与执行方案

日期：2026-10-20。状态：本地实现和验证已推进至 M7；实际结果见 REMEDIATION_RESULT.md 与各验证文件。真人需求、远程 CI、公开发布和送审仍未完成，不代表审核已接受。

## 1. 目标与产品边界

目标：以可运行的软件和可复核的使用证据，逐项回应场景狭窄、接入成本高、现有工具重叠、独立复用不足四项反馈，为重新送审准备材料。不能保证审核通过。

目标定位：EditTrace 是面向编辑器插件和语言工具开发者的文本变更验证与回归工具，覆盖格式化/代码修复、文本型重命名与文档同步。用户从真实日志或编辑器操作进入，得到变更预检、结果比较，并把问题保存为持续运行的回归用例。

保留现有同步审计能力；扩大相邻使用场景，不重写为完整 LSP 框架。验证文本适用条件和结果一致性，不证明程序语义正确，不从客户端记录推断服务器内部状态。

## 2. 缺陷复盘与经验

| 现有缺陷 | 形成原因/经验 | 必须改变的工作方式 |
|---|---|---|
| 以同步故障为唯一需求中心 | 从可实现的协议规则出发，缺少用户工作流验证 | 先完成格式化、重命名、同步三个真实任务，再扩展规则 |
| 用户先手写或转换 JSONL | 把内部格式误当产品入口 | JSONL 保留为内部格式，提供真实日志导入和编辑器采集 |
| 自动采集长期排在 P1 | 低估首次接入成本对工具价值的影响 | 接入闭环成为本轮必做项 |
| 三个场景只是同一故障的排查、回归和交接 | 场景数量替代了需求来源多样性 | 三个场景应有不同触发条件、输入和可观察产物 |
| 大量合成测试被用于支持应用价值 | 混淆引擎正确性、接入有效性和用户需求 | 三类证据分开记录，任何一种不能替代另外两种 |
| 差异主要是若干已有能力的组合 | 缺少相同任务下的直接对照 | 记录人工步骤、接入成本、实际产物和失败定位边界 |
| 公开接口偏向 feed_line 与 JSON | 内部可导入不等于外部容易使用 | 提供带类型的变更计划/断言接口和外部消费者示例 |
| 原始日志、编辑器事件、独立检查点容易混淆 | 采集来源与结论之间缺少明确契约 | 每份报告保留来源、编码证据、版本、顺序和不可比较原因 |
| 材料仍保留“仅格式驳回”的旧状态 | 工程状态和审核状态未统一更新 | 依据用户提供的本轮实质反馈更新，保留历史日期 |

今后每项功能先回答：谁在什么情况下使用、如何取得输入、得到什么可行动结果、如何验证、相比当前流程减少了什么工作。没有答案时不先堆功能。

## 3. 实施纪律

1. 先阅读 AGENTS.md、PLAN.md、docs/PROTOCOL_NOTES.md 和相关格式/规则；先检查工作区，保留用户已有改动。
2. 核心解析、文本语义、审计、断言、报告与用例运行保留在 MoonBit。TypeScript 仅承担 VS Code 接入、事件采集、宿主调用及必要格式桥接；Python 继续用于开发验证与打包。
3. 默认单代理连续推进。每阶段更新 PLAN.md 的独立整改章节和本方案进度表；不要覆盖既有验证历史。
4. 每阶段先跑相关检查，修复失败后继续。最终运行 native 测试、scripts/validate.py 和新增端到端检查。测试实际行为与边界，不以数量作为目标。
5. 旧四个 CLI 命令与 JSONL v1 保持兼容。新用例/批量编辑格式独立版本化，不把新事件硬塞进旧同步语义。
6. 不修改独立 oracle 期望以迁就实现；确需重生成只使用既定固定参考实现，并说明理由。
7. 可连续执行本地源码、测试、文档和打包工作；不要为普通实现选择反复询问。依赖用户/外部环境的证据标为未完成，继续其他工作。
8. 本任务执行提示词不授权推送、公开发布、报名提交或对外联系；如存在可核实的另行授权，以其具体范围为准。任何受阻动作写明原因，不用虚构结果代替。
9. 禁止把故障注入称为发现真实第三方缺陷；禁止把代理模拟试用当真人试用；禁止把演练计时当真实用户测量。

## 4. 架构与接口决策

建议模块（可结合代码现状调整，变更要记录原因）：

```text
原始 LSP JSON trace → adapters/vscode_trace ─┐
VS Code 文档采集/提供者结果 → 接入扩展 ───────┼→ 版本化内部事件/变更计划
外部 MoonBit 项目 → 带类型公共接口 ──────────┘
                         ↓
    core/text + core/session + core/edit_plan
                         ↓
      core/case（断言、批量运行）→ 报告/差异/用例包
```

先在 M0 冻结命令和格式，以下仅为候选：

```text
edittrace import <source-log> --from vscode-json --out <new-trace>
edittrace check-edits <edit-plan> --format text|json
edittrace case create <recording-or-plan> --expect <expectation> --out <new-directory>
edittrace case run <case-directory> --format text|json
edittrace suite run <suite-manifest> --format text|json
```

新命令延续 0=完整且通过、1=完整且断言/规则失败、2=输入或执行不完整。用例中预期出现 finding，且实际相符时，用例运行返回 0；其嵌套审计仍可能为 1/2，不得丢失该状态。预期 finding 的字段匹配方式必须显式，不能只对比脆弱的显示序号。

所有原文、URI、名称均视为外来数据。报告转义；HTML 如被采用需转义且不执行外部内容。采集只由用户显式启动，默认本地，具有停止入口和资源上限。用例中记录只通过清单允许的相对路径访问，拒绝路径逃逸，不执行用例附带脚本。

## 5. 阶段任务与验收

### M0：基线、范围与证据契约

工作：
- 读取代码与现有验收，运行基线，记录提交标识、工具链和真实结果；失败先区分历史问题和环境缺失。
- 在 docs/REMEDIATION_SPEC.md 冻结支持范围、三种编辑语义、来源字段、新格式与退出码。
- 建立 docs/competition/FEEDBACK_MATRIX.md，为四项质疑登记任务、证据路径、状态和剩余不足。
- 选择并固定可实际安装的 VS Code、languageclient、真实提供者/服务器版本。查阅官方文档与源码，不依赖旧示例猜测。
- 提前做最小接入探针，确认日志取得方式、格式化/重命名提供者结果取得方式和文档事件语义，记录不可用接口与替代路线。

验收：基线可说明；每个承诺都有输入、输出和验证方式；不把第三方扩展通信截获作为未经验证的前提。

### M1：真实日志直接导入

工作：
- 优先支持一个固定、实测的 vscode-languageclient JSON trace 方言，先支持该格式，不能宣传兼容任意日志。
- 自动生成内部 meta/seq，保留原始顺序、方向、源行/记录位置与生产者信息；不按时间戳重排。
- 不补造缺失 didOpen、快照或方向；未知类型和不支持字段的处理策略清楚可查。
- 读取初始化编码协商：缺省依据、显式声明和用户覆盖分别记录；明确非 UTF-16 会话不能直接按 UTF-16 验证。
- 对截断、损坏、缺少正文、混合会话和资源上限给出明确错误或不完整结果；不能静默跳过关键事件后声称通过。
- 旧 v1 如无法表达来源细节，使用有版本的旁路清单，不破坏旧解析。

验收：至少一个真实客户端/服务器会话无需人工改写即可导入并审计；带正常编辑、Unicode、多文档、关闭重开；具备损坏/截断和编码不支持检查。仅导入成功不算检查点一致性已验证。

### M2：批量文本变更预检

工作：
- 新增 core/edit_plan，支持 TextEdit[] 与 TextDocumentEdit，以及只含受支持文本编辑的 WorkspaceEdit 子集。
- 区分 didChange 顺序语义、TextEdit 同一基线语义和 VS Code 文档事件语义；后者先验证再适配，不直接复制数组为 didChange。
- 检查范围、Unicode 边界、重叠、同位置插入顺序、版本匹配及重复文档操作；按规范实现并记录保守策略。
- 输入必须有明确文本基线；无版本约束的输入标为版本未验证，不虚构“已检查版本”。
- 计算预期结果，可与独立取得的实际结果比较；不以本核心的输出生成所谓独立预期。
- 资源文件操作、未知编码或不支持结构显式失败/不完整，不忽略后宣告通过。第一版只做预检和预览，不自动改写用户工程。

验收：真实格式化结果与实际应用后文本一致；文本型跨文件重命名可验证；版本过期、编辑重叠、CRLF、emoji、同位置插入有针对性检查。至少一组批量编辑由固定独立宿主或参考实现核对。

### M3：最小 VS Code 接入

工作：
- extensions/vscode 提供开始记录、停止并分析、查看差异、保存回归用例等入口；保持简单，不先开发大型 Webview。
- 记录开始时对选择的已打开文档建立基线；维护事件前文本，观察每个事件后的实际文本，并记录版本与来源。
- 使用实际事件输入重放，与宿主实际文本对照；若丢事件或版本断裂，标记不完整，不用全文快照掩盖遗漏。
- “文档事件录制”与“LSP 通信审计”分别展示证据范围；普通文档事件不能证明服务器收到的消息。
- 提供受控的“验证格式化结果/验证重命名结果”入口：通过官方提供者命令取得候选编辑，在临时测试工作区预检、应用并比较。不能声称任意第三方操作均可无侵入拦截。
- 用户工程默认只读预览。真实应用演练限定测试工作区；版本在计算到应用之间变化时拒绝继续，部分应用失败明确报告。
- 核心调用使用参数数组，不拼接 shell；支持路径有空格、取消、超时、缺少二进制及非零退出码。

验收：真实 Extension Host 中完成三类操作；多光标/批量事件、撤销重做、录制开始前已打开文档、停止后无继续记录均验证。仅 Node 单元测试不能代替 Extension Host 集成结果；无法运行时如实留缺口。

### M4：用例、断言与外部 CI

工作：
- 定义 case/suite 清单，包含格式版本、基线、操作、预期、来源、版本和必要资源。
- 同时支持“目标 finding 应能复现”和“修复后文本/规则应通过”；明确断言及完整性要求。
- 支持最终文本、指定步骤文本、指定 finding、无指定 error、分析完整性等有意义断言。
- 报告清楚列出期望与实际，不用新运行结果自动覆盖 golden 文件。
- 导出后在新目录运行；保留原始输入与必要依赖，禁止依赖原工程绝对路径。
- 提供带类型公共 API 和单独消费者示例，用本地依赖完成编译与执行。未真实发布前不得伪称注册表安装成功。
- 增加“外部插件/语言工具使用 EditTrace”的 CI 示例，与 EditTrace 自测 CI 明确区分。

验收：同一套用例正常通过；改变编辑范围、预期文本、版本或目标规则后产生正确失败；缺失依赖返回不完整；外部消费者不修改 core 即可运行；迁移目录后结果稳定。

### M5：报告与复现交付优化

工作：
- 输出用户能理解的文件、操作、版本、预期/实际、差异及下一步检查建议；区分不一致观察和已证明根因。
- 只在证据支持时给出最后一致与首次不一致之间的区间；不能默认上一条编辑就是根因。
- 支持按文档筛选证据包并重新验证目标；依赖无法保持时保留原包，不能交付失效裁剪。
- 整理确定性输出、资源限制、隐私说明和报告摘录策略；不把隐藏摘录称为完整脱敏。

验收：接收者无需原工程即可执行；报告能解释失败及不可比较原因。自动 delta debugging 属于可选项，只有 M0–M4 通过后实施；不承诺全局最小复现。

### M6：发行与首次使用

工作：
- 在已有 Windows/Linux CI 上构建适配平台的发行包，包含二进制、许可证、示例、校验清单与快速开始；以实际成功平台标识支持范围。
- 生成可侧载 VSIX，并明确兼容的宿主/平台；不要求普通用户安装 MoonBit 编译工具链。
- 扩展使用配置路径或打包二进制，方案取决于实测平台支持；不静默联网下载或修改系统环境。
- 以干净目录完成“取得产物→导入/录制→报告→运行用例”的演练，记录步骤、依赖、时间和环境。

验收：目标为受支持环境下五分钟首次报告；实际是否达标必须计时测量。开发者演练与真人试用分开记录。没有 Linux 环境时可写 CI 产物准备就绪，不能伪称 Linux 人工操作已验证。

### M7：真实证据与重新送审材料

工作：
- 在 examples/real-world（或同等目录）提供三类实采任务：格式化、文本型跨文件重命名、同步。记录软件版本、步骤、原始来源和预期。
- 独立标记正常真实采集、真实链路故障注入、历史缺陷复现；有些类别缺失就如实说明。
- 故障注入至少覆盖一次错误范围/过期版本/漏事件；用来证明检测能力，不能当作发现第三方漏洞。
- 使用同一输入，对照人工日志查看或现有检查工作流，记录操作步骤与产物；只比较实测能力，不推断其他工具没有未阅读的功能。
- 准备试用说明与反馈表，供用户邀请真实维护者体验。没有授权不对外联系；缺少真人需求证据时保留待验证项。
- 更新 README、LIMITATIONS、ARCHITECTURE、TRACE_FORMAT、AI_USAGE 及参赛材料；纠正仅格式驳回的过时状态，明确两条实质反馈为用户提供。
- 草拟一页申报材料和三分钟演示。核实当前官方赛事要求与截止日期；遵守已核实的人工定稿要求，不声称 AI 草稿已满足该要求。

验收：四项反馈逐项有交付、证据、局限；材料只陈述已完成能力。真人反馈、包发布、远程 CI 和正式提交分别记状态，不能由本地成功代替。

## 6. 优先级与停止扩张规则

- 必做：M0–M4、M5 的基本报告与可运行包、M6、M7 的可执行演示和事实更新。
- 后置：复现序列自动缩减、漂亮时间线、第二种日志格式、更多编辑器、完整 WorkspaceEdit 资源操作。
- 本轮排除：云端平台、完整 LSP 合规认证、AI 根因保证、语义正确性证明、无边界插件兼容。
- 遇到进度压力，删除后置功能，不能删除真实入口、至少一个新增日常场景或回归闭环后仍宣称反馈已全面解决。
- 不预设审核日期或固定开发工期；M0 后按探针结果估算，并以剩余验收项调整。

## 7. 全局完成标准

以下是工程整改完成条件，不是赛事通过保证：

- [x] 原有 CLI 与输入格式回归通过，已有 oracle 保持独立。
- [x] 一种真实日志无需用户转换即可导入，错误/截断不会被静默吞掉。
- [x] VS Code 真实宿主中能够取得基线、记录操作并生成报告。
- [x] 格式化、文本型跨文件重命名、同步三类任务各有真实输入和可执行演示。
- [x] 批量编辑预检有独立参考，不混用三种编辑语义。
- [x] 用例可导出、迁移、批量运行，并明确复现与修复断言。
- [x] 独立消费者及外部项目 CI 示例无需修改核心即可使用（本地消费者已运行；新远程 CI 未执行）。
- [x] Windows 本地发行包与 VSIX 可构建/安装，支持范围由实际验证确定；Linux 新发行待 CI。
- [x] 验收脚本实际执行新增断言，且错误用例要求正确非零退出码。
- [x] 四项反馈有明确对应证据；未获真人反馈时需求规模仍标为待验证。
- [x] 文档、帮助、版本、兼容范围及示例已同步，发布与正式送审状态真实。

最终报告分别给出：已实现、实际验证、未验证/外部依赖、仍有风险。不得把四类混合为“全部完成”。
