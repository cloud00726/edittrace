# EditTrace 后续版本防回归改进方案

核查日期为 2026-11-13。针对赛事组反馈「声明的功能不足以支持所承诺的插件或语言工具后续版本防回归」，交付目标是让维护者在自己的 CI 中用固定输入和已审核的预期结果，重新执行待发布版本的实际操作，并在行为退化时阻断合并或发版。

## 一、现有能力与证据

| 核查对象 | 已验证的能力 | 与反馈相关的缺口 |
|---|---|---|
| [申报书](APPLICATION_REMEDIATED.md) | 描述格式化、跨文件重命名和同步复现三个场景，承诺把采集用例用于后续版本的持续回归 | 混用了离线重放和验证新版本这两种流程 |
| [公开 Release 0.2.0 Preview 1](https://github.com/cloud00726/edittrace/releases/tag/v0.2.0-preview.1) | 核对 Windows/Linux 四个本地归档副本与 GitHub 资源 SHA-256 一致。Windows VSIX 包含录制、格式化、重命名、保存用例、差异查看等六个命令。实跑原生工具，冻结 suite 返回 0，丢事件故障用例返回 1 | 发行包提供采集和离线用例运行。随仓库提供的消费者 CI 同样仅重放已保存 suite |
| [公开 main 的 0.4.0 源码](https://github.com/cloud00726/edittrace/commit/bf2a74edf3477ee76e2bd163ab3d8643d53d452f) | [Windows/Ubuntu CI](https://github.com/cloud00726/edittrace/actions/runs/41014987545) 均通过。源码含项目用例审核、JUnit、分享、复现缩减。用本地 0.4.0 重跑同一 suite 与负例，分别返回 0 和 1 | GitHub Releases 列表仅有 0.2.0 预览版。0.4.0 的项目回归仍组合并执行冻结 case，仓库双平台 CI 验证 EditTrace 自身 |
| [真实 VS Code 宿主记录](../STAGE2_RESULT.md) | 测试代码调用了 JSON 格式化、TypeScript 跨文件重命名，并在宿主应用编辑后读取实际文本 | 独立应用发生在宿主测试代码。用户预检命令只取编辑与基线。已有记录缺少固定基线与待测版本之间的行为比较，也缺少真实 MoonBit 提供者的版本验证 |

代码证据见 [扩展实现](../../extensions/vscode/extension.js)、[项目用例发现](../../extensions/vscode/project.js)、[MoonBit case 运行器](../../core/case/case.mbt)及[消费者 CI 示例](../../examples/ci-consumer/workflow.yml)。`formattingPlan` 和 `renamePlan` 在采集时调用提供者。`makeCaseDraft` 保存当时的编辑计划，初始文本断言来自当时核心报告中的预测结果。`runSuite` 把已确认文件组装成 suite，MoonBit 对其中保存的计划或记录求值。即使待测插件新版已经漏掉第二个文件的重命名，旧用例仍会重放当初包含两个文件的编辑并通过。只有执行待测版本、观察新结果并与固定预期比较，才能发现这次漏改。

## 二、实施顺序与验收

### R0 固定反例与支持范围

- 先做两文件重命名反例。固定输入包含定义与引用，正确版本改两处，故障版本只改定义。保留一份旧 case，记录其仍通过。接下来用同一工程与断言对两个可安装版本运行新版验证入口，要求好版本返回 0，漏改版本返回 1。
- 首期支持 Windows 与 Ubuntu CI 上经验证的 VS Code 格式化和跨文件纯文本重命名，以及可通过固定客户端动作重现的文档同步场景。文本比较针对声明的文件与观察点。LSP 工作区资源操作、服务端内部状态和语言语义正确性按实际能力披露。
- 将原有 case/suite v1 继续用于 EditTrace 自身回归、离线复现与证据交接。新增可执行场景格式并独立标版本，避免旧文件升级后被默认为已验证新提供者。

### R1 定义可执行场景与审核基线

- 场景记录工程快照及文件哈希、语言及操作、操作参数、固定目标文件、受检文件范围、预期文本或检查点、宿主和工具链约束。重命名参数含起始文件、位置与新名称。同步参数含固定动作序列与宿主观察点。运行参数另行指定被测制品及哈希，不写入期望。
- 期望来自人工审核过的正确结果或独立宿主实际结果，记录来源、基线版本及哈希。历史预测结果可导入为待审核草稿。基线晋升要求显式确认及查看差异，PR 验证期间基线只读。受检文件默认包含声明范围内的所有文件，分别断言该改、禁止改和最终文本。新出现的额外文件或未声明修改按支持契约拒绝或报告失败。
- 验收包括基线变更可审查、候选运行前后基线哈希相同、换行和 Unicode 不被意外归一化、空场景或缺少必要断言时无法产生通过结果。

### R2 让 CI 真正执行待测版本

- 建立隔离 VS Code 执行器，固定宿主版本、依赖、工作目录与设置。每条场景从同一个干净副本启动。安装仓库本次构建的候选 VSIX 或明确指定的固定版本。记录实际激活的扩展标识、版本、制品哈希与必要的语言服务器版本。对于可重现环境只启用指定提供者与必要依赖。宿主无法可靠确认实际提供者时，报告验证未完成。
- 格式化与重命名均在运行时取得新编辑。在临时工程用宿主应用结果并读取实际文本，MoonBit 另算预测结果。分别比较「预测与宿主实际」及「宿主实际与已审核预期」。两者回答不同问题。跨文件改名前锁定声明的文件基线，检查应修改的引用文件有没有出现在实际结果中。
- 同步场景在待测环境重新执行固定客户端动作，采集新的事件、版本与宿主快照，再做 MoonBit 重放。可从受测对象直接观察的结果才作为针对其行为的断言。仅能观察编辑器侧同步时，场景标为客户端同步回归。
- 执行器负责启动、采集与隔离。MoonBit 负责场景校验、结果比较、判定与报告。缺失提供者、没有完成请求、超时、路径逃逸、不支持的操作和制品版本不符，均给出独立诊断。只有场景明确允许无编辑，且实际提供者执行可确认时，无编辑才可通过。每次运行限定时间、输入大小及文件范围。
- 验收覆盖格式化错误、重命名漏改和误改、同步丢事件或乱序、提供者缺失与超时。失败报告带场景、目标版本、文件与差异位置。确认故障时目标断言失败，确认环境故障时结果不可用。

### R3 在独立消费者工程证明会拦截发布

- 建一个仓库外的最小消费者工程，用其自身的 CI 从固定制品安装 EditTrace 和待测插件。由消费项目定义场景与已审核基线，直接验证本次构建的候选。接入示例从这个实际工作流提炼。
- 三场景分别提供正确版本、故障版本及修复版本的执行记录。优先采用可复核的历史回归。没有真实历史缺陷的路径使用明确标注的故障注入，并额外保留真实提供者的运行证据。至少一个独立消费者工作流真实执行失败的合并检查，再记录修复后的通过。测试驱动可验证负例返回码，消费者门禁本身须实际失败。
- 建议入口 `edittrace provider run <scenario-suite> --candidate <artifact>`，命名可在实现时调整。JSON 与 JUnit 采用同一判定，0 为通过，1 为行为回归，2 为运行或证据不完整。1 和 2 都阻断门禁。CI 上传默认不含完整源码的摘要，包含制品哈希、基线哈希、场景结果、宿主和工具版本。完整差异在本地或明确允许的工件中查看。
- 对 MoonBit 生态分别记录真实扩展/语言服务器用例与 MoonBit 库消费。没有可用的受测 MoonBit 工具版本时，仍完成已有提供者的验证，并按已实测范围表述。

### R4 发行与申报对齐

- 从通过门禁的同一源码提交生成 Windows/Linux CLI 与 VSIX。对最终下载包复核哈希、安装及独立消费者入口。发行页、快速开始、申报书和演示使用同一真实可下载版本与可访问的成功和失败 CI 链接。保留旧版链接供历史核查。
- 在 R3 有证据前，申报口径使用「保存并重复执行已采集的文本编辑用例，用于离线复现与验证」。R3 完成后，可写为「在固定 VS Code 环境中执行待测版本的格式化和跨文件纯文本重命名，以已审核结果阻断已配置场景的行为回归」。同步和 MoonBit 提供者承诺分别依据其实际通过范围追加。
- 最终验收交付可下载制品、固定版本清单、三场景与基线、消费者 CI 配置、好版通过及坏版失败链接、修复版通过链接和短演示。历史报告保留当时状态。公开 Release、Mooncakes 与赛事提交按相应授权和当前赛事渠道处理。

首个可交付里程碑是两文件重命名在独立消费者 CI 中对漏改版本实际失败、对修复版本通过。用同一机制扩展格式化与同步场景，再准备发行与申报证据。
