# EditTrace 持续维护与价值提升方案

日期：2026-10-25。定位：面向编辑器插件与语言工具维护者的文本变更验证、证据交接与持续回归工具。本文是后续开发任务及验收约定，未实现的功能均为计划，不视为交付成果。

## 1. 维护目标与当前基础

主线保持为“采集真实操作 → 检查编辑结果 → 解释差异 → 保存明确期望 → 持续回归”。优先服务格式化、跨文件文本重命名及文档同步三个已验证场景。每项新增功能必须说明具体用户、触发任务、输入、输出和可执行验收。

当前已有 MoonBit 文本与审计核心、CLI、VS Code 录制/预览、case/suite、独立工作区消费者及 Windows/Linux 预览产物。已有测试证据见 VALIDATION.md、PUBLISHING_RESULT.md；历史通过数字不自动沿用到新版本。核心语义保持在 MoonBit，扩展负责采集、展示与宿主交互。

本次源码核查发现的主要维护空间：

- 扩展主要打开 JSON 报告，跨文件差异仅展示首个文件，用户仍需理解报告结构。
- 保存的是回归草稿，录制结果不等于正确期望，进入长期回归缺少清楚的审核状态与操作流程。
- case/suite 已存在，但缺少面向普通项目的初始化、发现、运行摘要及 CI 接入指导。
- 类型接口已可被本地消费者调用，但模块仍为 local/edittrace，注册表安装和外部消费尚未完成。
- README、限制和历史核查文件存在过期状态；CLI 新能力集中在上方示例，完整命令参考需要统一。
- 性能只记录过有限样例，缺少可重复的规模与内存基线；真实维护者持续使用证据仍不足。

## 2. 版本推进顺序

| 阶段 | 建议范围 | 用户得到的改善 | 完成依据 |
|---|---|---|---|
| R0 / 0.2.1 | 文档、诊断与发布准备 | 知道怎么安装、当前支持什么、失败如何处理 | 干净安装演练、文档命令实跑、许可清单、候选包清单 |
| R1 / 0.3.0 | 易读报告、多文件差异、回归管理、CI 结果 | 一次发现的问题可以方便地持续检查 | 真宿主操作、失败用例、迁移重跑、示例 CI |
| R2 / 后续小版本 | MoonBit 注册表消费与生态示例 | 在自己的 MoonBit 工具中调用验证能力 | 发布回执、脱离工作区的独立安装和调用 |
| R3 / 0.4.0 候选 | 复现缩减、实测性能、按需求增加适配器 | 更快交接真实问题，更好处理大型输入 | 保持目标故障的缩减证据、可复核基准、适配器真实样例 |

先完成 R0，再按 R1 的任务逐项交付。R2 的准备可与 R1 并行进行；正式命名空间调整及发布前先确定 API 和包内容。R3 根据真实任务选择，不要求一次实现全部。

## 3. R0：稳定交付与接入诊断

### R0.1 统一文档入口

- README 首页按“安装发行版、录制自己的操作、运行现成回归、MoonBit API 开发”四个入口组织；参赛历史移动到 competition 目录。
- 维护一份完整 CLI 参考，覆盖 import、check-edits、case、suite 及原命令；为每类失败提供最小示例与处理办法。
- 更新 LIMITATIONS 与状态说明，区分当前发布版本、源码版本及历史证据；修复“新 Linux CI 尚未运行”等过时描述。
- QUICKSTART 分清仓库样例路径与解压发行包路径。所有可复制命令必须在相应目录实际执行。

验收：独立新目录可完成一次安装、一次正常用例和一次预期失败；失效链接与示例路径为零；不将故障样例的退出 1 误写成安装失败。

### R0.2 接入诊断

计划新增 CLI `doctor`，并由 VS Code 命令调用；该名称为拟定接口。显示核心路径/版本、宿主版本、平台与支持范围、扩展和核心兼容情况。格式化/重命名入口区分“无提供者”“无编辑返回”“提供者错误”“超时”“输入不支持”，避免统一提示为成功或空结果。接口无法区分的状态明确说明证据不足。

验收：缺失可执行文件、版本不兼容、无提供者及超时各有可行动提示；诊断不打印凭据、源文件内容或自动修改设置。

### R0.3 许可和发布准备

保留 MIT 主许可证；核对 async、core 与开发参考实现的许可和归属。生成候选包文件清单，检查排除凭据、本地用户数据、宿主测试配置、个人绝对路径和非必要产物；独立核对最终归档内的许可文件。准备 Mooncakes 元数据、API 文档、迁移说明与版本映射。

验收：候选 ZIP、VSIX、Mooncakes 包清单可审阅；二进制版本、扩展版本、源提交及校验和能对应。包发布遵循官方[包管理与发布说明](https://docs.moonbitlang.com/en/latest/toolchain/moon/package-manage-tour.html)，同时核对固定项目工具链支持的实际命令，不能直接套用 nightly 新选项。

## 4. R1：把验证能力变成日常维护流程

### R1.1 易读结果与多文件差异（最高功能优先级）

扩展增加结果摘要与文档列表：显示处理是否完整、首个失败、涉及文件、规则原因、基线版本是否已检查、建议下一步。支持选择每个变更文件查看基线与预测结果，有实际快照时再显示预测与实际的差异。保存原始 JSON 入口便于排查。

“预检通过”“与独立实际文本一致”“缺少实际快照”必须是不同状态；文本验证通过不显示为重构语义正确。报告展示需转义输入内容，无法解析的报告不作成功处理。

验收：真实两文件重命名可分别打开两个文件的差异；Unicode/CRLF 差异位置正确；部分文件失败时全局摘要不误报通过；无实际快照时不会伪造 actual。

### R1.2 回归用例管理

新增项目级测试目录约定，支持发现现有用例、单例/整套运行及失败跳转。提供初始化 suite 的操作，并明确兼容现有 case/suite v1。草稿保存时保留来源与采集条件，显示“待确认期望”；审核动作由用户确定正确输出或故障预期，不自动把当前结果当作正确答案。

期望变化必须产生可见差异。即便后续增加更新基线命令，也须显式执行、列明变化，不因 CI 失败自动覆盖。审核元数据优先放在旁文件；如修改 schema，需版本化并提供迁移和旧版读取验证。

验收：录制正常场景、保存草稿、确认期望、加入 suite、故意引入差异并检出、迁移新目录重跑，整条路径可执行；故障复现成功和产品行为正常分别展示。

### R1.3 CI 结果交付

在现有 suite 上提供易读运行摘要和 JUnit 输出，列出全部失败与输入错误，保留 0/1/2 退出语义。提供独立示例工程演示安装固定版本、运行回归、上传失败证据。默认失败摘要减少源码暴露，包含原文的附件需明确选择。

验收：成功、预期故障复现、断言失败、损坏用例、多个失败均在结果中完整显示；一个损坏用例不阻断其余可运行用例；XML 转义、相对路径、Windows/Linux 行为一致。

### R1.4 可分享证据

先实现 URI/工程路径的确定性匿名化与分享清单预览，并保持同一文档映射一致。源码内容替换可能改变 UTF-16 长度、换行和故障，因此不默认提供“全量安全脱敏”承诺。任何会话转换后必须重跑并确认指定目标；变化后无法复现则不得标为验证成功。

验收：相同 URI 在消息、期望与清单中一致映射；筛选后的包能在新目录验证；报告明确哪些原文仍保留。遇到必须依靠源码复现的情况提示用户选择，不能悄悄删除证据。

## 5. R2：形成可消费的 MoonBit 生态能力

- 明确公共 API：文本位置与编辑类型、批量编辑验证、同步状态与结果、回归断言；为调用者提供类型化错误或结果，逐步减少只接收/返回 Json 的接口。
- 保留现有 API 的兼容层，固定公共接口快照与迁移说明；优先在现有模块内整理包边界，不为满足发布形式过早拆分多个模块。
- 检查纯计算包能否脱离 native IO/async 编译；实际验证通过后再声明可用后端。不要凭纯函数形态推断 js/wasm 已支持。
- 确定账户实际拥有的 Mooncakes 命名空间，统一模块路径、消费者 import、生成接口与文档。
- 在授权发布后，从注册表固定版本安装到独立工程；禁用本地工作区替代路径，运行格式化编辑检查和同步/回归示例。
- 增加 MoonBit 源码编辑场景：调用实际 MoonBit 提供者采集格式化或重命名，记录工具链、扩展和提供者版本；缺少提供者支持时明确记录，不以模拟返回冒充真实集成。

验收：公开包页和版本可核实；独立消费工程有依赖锁定和 CI；至少一个真实 MoonBit 工程场景能重复运行。包可安装不等于外部已采用，两类证据分别记录。

## 6. R3：基于真实任务扩大能力

### R3.1 故障保持的复现缩减

针对同步输入先做单文档、依赖感知的事件缩减：保留必要基线和目标检查点，以固定规则、文档身份、完成状态及期望差异作为保持条件。给出执行预算、取消能力和原始序号映射。预算耗尽可返回已验证的更小样例，不称全局最小。

验收：原始样例保留；每个交付候选均能独立复现指定目标；截断、损坏和任意退出 2 不能替代原目标；关闭重开、多文档依赖不能被错误删除。

### R3.2 性能与资源可预测性

建立确定种子的规模矩阵，覆盖 10 KiB/100 KiB/1 MiB 文档、不同编辑数、多文件、Unicode、长行、全文替换和大批量编辑。记录构建模式、工具链、机器、输入哈希、预热、重复次数、中位数、波动及峰值内存测量方法。性能阈值须先有可信基线，再决定是否作为 CI 阻断项。

按剖析结果优化行索引、文本复制或快照处理；只有实测瓶颈才引入复杂数据结构。任何优化均跑原独立参考语料及故障路径，保留相同输出语义。默认 CI 只放稳定的小规模防退化样例，大基准手动执行。

### R3.3 新输入适配器

新增适配器必须来自真实试用需求，优先选择一种具体客户端日志方言或一种提供者输出。每个适配器需真实匿名化输入、格式版本、方向/编码/初始化证据和截断失败样例。暂不同时扩展多种编辑器、非 UTF-16 编码或完整 WorkspaceEdit 资源操作；如用户任务依赖这些能力，单独制定语义与验收契约。

## 7. 长期仓库维护规则

| 对象 | 维护动作 | 完成标准 |
|---|---|---|
| 提交历史 | 一项可解释的修复或能力一个提交；必要文档和测试同批更新 | 提交能说明问题、行为变化与验证，不按数量拆空提交 |
| README | 维护当前安装、完整入口、支持矩阵及文档导航 | 新用户无需阅读参赛历史即可完成首次报告 |
| 使用文档 | 示例按发布版运行；区分源码/归档目录 | 复制即可执行，预期退出码明确 |
| API/schema | 明确兼容策略，公开变化提供迁移示例 | 历史用例可读；破坏性变化不会静默接受 |
| LICENSE/来源 | 新依赖进入时核对许可、用途、分发归属 | 归档中许可齐全；依赖用途与实际一致 |
| 测试与 CI | 以故障风险选测试；固定工具链稳定构建，升级另分支验证 | 失败不上传旧报告冒充本次成功；独立参考不随意重生成 |
| 问题反馈 | 收集任务、版本、输入范围、预期和实际，确认后建回归 | 关闭缺陷时保留复现及防回归依据 |
| 发布 | 版本说明、源提交、平台包、校验和与实际测试状态关联 | 发布附件来自已通过检查的同一源码 |

建议每周一次问题分级和文档巡检；每两周或完成一项有用能力后评估候选版本。紧急正确性问题优先补丁发布，发布频率服从质量。维护计划不是后台定时任务，需实际执行后再记录结果。

## 8. 真实价值验证与取舍

邀请格式化、语言服务或编辑器插件维护者用自己的项目完成任务，记录首次报告所需主动时间、人工转换步骤、误报与漏报、保存用例数、后续运行及失败排查帮助。目标样本可从 2–3 位开始，该数量是维护建议，不是统计证明或赛事硬性条件；未经授权不替用户联系他人。

每一项功能在开始前写明“哪类用户的哪一步将减少什么工作”；完成后用同一任务比较操作与输出。没有预期收益或没人愿意保存回归时，优先简化流程或调整任务选择，不以增加功能数量代替证据。个人自动演练、真人主观反馈、外部持续采用分别记录。

## 9. 首批可直接执行任务

按 R0.1 → R0.2 → R0.3 → R1.1 → R1.2 → R1.3 推进，每项完成后再接下一项。R2 先做 API/发布准备，发布需具备账户与明确授权。R1.4 和 R3 按真实试用结果排序。

每项交付应包含：实现、必要回归、更新后的用法与限制、实际命令结果、可审阅 diff。改动产品时按 AGENTS.md 运行 native 测试及 scripts/validate.py；宿主相关变更补真实 Extension Host 检查，发行变更补归档独立验证。仅文档修订不重复产品全量测试，核对命令、链接与 git diff --check。

建议安排首个六天执行窗口，工作量为估算：前两天完成 R0；第三至四天完成 R1.1 和回归管理的最小版本；第五天做 CI 结果及生态消费准备；第六天修复、实际演练与候选证据整理。若遇到正确性问题，缩减范围并如实列出未完成项，不为赶日期改变断言或声称验收已通过。后续两至四周再根据试用推进 R2/R3。

本文不把功能规划当成赛事合规结论，也不替代最终材料核对；实际章程核查见 competition/SUBMISSION_AUDIT_2026-10-21.md。
